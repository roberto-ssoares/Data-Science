## 1. Proposta de valor

Construir um MVP analítico para identificar **padrões suspeitos em transações financeiras**, simulando um ambiente de conta corrente/PIX/cartões, usando:

- **dados transacionais sintéticos**;
- **regras antifraude explicáveis**;
- **grafo de relacionamento entre entidades**;
- **métricas de centralidade**;
- **detecção de comunidades suspeitas**;
- **score analítico de risco por cliente/transação**;
- **dashboard executivo/investigativo**.

Isso conversa diretamente com a vaga, porque ela pede monitorar, identificar e investigar padrões de fraude, desenvolver e evoluir regras, fazer EDA, apoiar decisões com SQL/dados e documentar aprendizados.

## 2. Por que grafos fazem muito sentido aqui?

Fraude transacional raramente aparece isolada. Muitas vezes ela aparece em **relações indiretas**:

- vários clientes usando o mesmo dispositivo;
- várias contas recebendo dinheiro de uma mesma origem;
- muitos PIX em sequência para um mesmo recebedor;
- contas novas conectadas a recebedores recorrentes;
- cartões/dispositivos/contas compartilhando padrões;
- pequenos grupos operando em comunidade;
- “contas ponte” movimentando valores entre grupos.

É exatamente onde grafos brilham.

A biblioteca **Neo4j Graph Data Science** possui algoritmos de centralidade para identificar nós importantes em uma rede, o que pode ajudar a localizar contas, dispositivos ou recebedores com comportamento estruturalmente relevante.  
Também há algoritmos de comunidade, como **Louvain**, que detecta grupos densamente conectados, útil para encontrar possíveis clusters coordenados.  
E o **Weakly Connected Components** identifica conjuntos de nós conectados, mesmo em grafos direcionados, o que ajuda a mapear redes de relacionamento suspeitas.

## Entidades do grafo

| Nó                | Exemplo                         |
| ----------------- | ------------------------------- |
| `Cliente`         | pessoa física ou conta bancária |
| `Conta`           | conta corrente ou carteira      |
| `Transacao`       | evento financeiro               |
| `Dispositivo`     | celular, browser, device_id     |
| `IP`              | endereço IP ou faixa            |
| `Beneficiario`    | recebedor da transação          |
| `Cartao`          | cartão vinculado                |
| `Estabelecimento` | merchant ou canal               |
| `Regra`           | regra antifraude disparada      |

## Relacionamentos

| Relação                                             | Significado                              |
| --------------------------------------------------- | ---------------------------------------- |
| `(:Cliente)-[:POSSUI]->(:Conta)`                    | cliente possui conta                     |
| `(:Conta)-[:REALIZOU]->(:Transacao)`                | conta realizou transação                 |
| `(:Transacao)-[:ENVIOU_PARA]->(:Beneficiario)`      | destino do PIX/transferência             |
| `(:Transacao)-[:USOU]->(:Dispositivo)`              | dispositivo utilizado                    |
| `(:Transacao)-[:ORIGINOU_DE]->(:IP)`                | IP da origem                             |
| `(:Transacao)-[:ACIONOU]->(:Regra)`                 | regra disparada                          |
| `(:Conta)-[:COMPARTILHA_DISPOSITIVO_COM]->(:Conta)` | ligação indireta suspeita                |
| `(:Conta)-[:CONECTADA_A]->(:Conta)`                 | conexão derivada por comportamento comum |

## 4. Dados: sintéticos ou públicos?

Para esse caso, eu recomendo **dados sintéticos primeiro**.

## Por quê?

Porque dados reais de PIX, conta corrente e antifraude bancária são altamente sensíveis. Um dataset sintético bem desenhado permite simular:

- contas normais;
- contas novas;
- comportamento de fraude;
- transações em rajada;
- valores atípicos;
- múltiplos clientes usando mesmo dispositivo;
- recebedores concentradores;
- circularidade de dinheiro;
- horários incomuns;
- regras acionadas.

Para portfólio, isso é ótimo porque demonstra **domínio conceitual e técnico**, sem depender de dado bancário real.

Depois, em uma segunda versão, podemos conectar com um dataset público de fraude em cartão ou transações para complementar o projeto. Mas para a vaga do Agibank, eu começaria com **dataset sintético orientado ao domínio da vaga**.

## 5. Regras antifraude do MVP

O projeto precisa mostrar que você sabe pensar como prevenção a fraudes, não apenas como modelagem.

Exemplos de regras:

| Regra                              | Descrição                                                |
| ---------------------------------- | -------------------------------------------------------- |
| `R001_TRANSACAO_ALTO_VALOR`        | valor muito acima do padrão histórico do cliente         |
| `R002_MULTIPLOS_PIX_CURTO_PERIODO` | muitas transações em janela curta                        |
| `R003_DEVICE_COMPARTILHADO`        | mesmo dispositivo usado por várias contas                |
| `R004_BENEFICIARIO_CONCENTRADOR`   | recebedor recebe de muitas contas diferentes             |
| `R005_CONTA_NOVA_ALTO_VALOR`       | conta recém-criada fazendo transações altas              |
| `R006_HORARIO_INCOMUM`             | transação fora do padrão horário                         |
| `R007_IP_COMPARTILHADO`            | muitas contas operando do mesmo IP                       |
| `R008_COMUNIDADE_SUSPEITA`         | cliente pertence a cluster com alta incidência de fraude |

## 6. Criar ambiente com `uv`

Se estiver usando `uv`, rode:

```powershell
uv venv  
.venv\Scripts\activate  
uv sync
```

Depois registre o kernel do Jupyter:

```powershell
python -m ipykernel install --user --name fraud-graph-analytics --display-name "Python 3.12 - Fraud Graph Analytics"
```

## 8. Criar o repositório no GitHub

Você pode criar pelo site do GitHub com estas configurações:

| Campo           | Valor recomendado                                                                               |
| --------------- | ----------------------------------------------------------------------------------------------- |
| Repository name | `fraud-graph-analytics`                                                                         |
| Description     | `MVP de prevenção a fraudes transacionais com Knowledge Graph, regras explicáveis e CRISP-DM+.` |
| Visibility      | Public                                                                                          |
| Add README      | Não, porque já criaremos localmente                                                             |
| Add .gitignore  | Não                                                                                             |
| License         | Pode deixar sem por enquanto                                                                    |

Depois que criar o repositório no GitHub, ele vai mostrar comandos parecidos com estes. Use adaptando para seu usuário:

```powershell
git branch -M main  
git remote add origin https://github.com/SEU-USUARIO/fraud-graph-analytics.git  
git push -u origin main
```

No seu caso provavelmente ficará algo como:

```powershell
git branch -M main  
git remote add origin https://github.com/roberto-ssoares/fraud-graph-analytics.git  
git push -u origin main
```

## 9. Primeiro README simples, só para abrir o projeto

No `README.md`, cole por enquanto:

```textile
Fraud Graph Analytics

MVP de prevenção a fraudes transacionais com **Knowledge Graph**, **regras explicáveis**, **análise de redes** e **CRISP-DM+**.

## Objetivo

Construir um projeto analítico para simular, detectar e explicar padrões suspeitos em transações financeiras, combinando:

- dados sintéticos orientados ao domínio de fraude;
- regras antifraude explicáveis;
- modelagem em grafo;
- algoritmos de centralidade e comunidades;
- score de risco transacional;
- documentação executiva para portfólio.

## Metodologia

Este projeto segue uma abordagem baseada em **CRISP-DM+**, enriquecida com:

- Ontologia;
- Business Language Model;
- Taxonomia de fraude;
- Knowledge Graph;
- análise de padrões transacionais;
- explicabilidade operacional.
